## Audit findings

- [x] Audit finding: `snapshotAll` recovery anchor took `history.first().id` (src/library.cpp:226), and `revisions` sorts by `id DESC` (src/library.cpp:85) — i.e. the newest (largest id) revision as "last clean revision (pre-infection)". But after ransomware rewrites the workspace, `scanChanges` (2s, src/mainwindow.cpp:102) races `pollSentinel` (5s, src/mainwindow.cpp:108): if auto-record captures the encrypted content as a "preserve-before-restore" revision before the sentinel alerts, that revision becomes `history.first()`, and the anchor points at infected content rather than pre-infection, so rollback restores the encrypted version — violating 85-antiransom.md:36 "anchor always points to a rollback-able pre-infection state". **Verified and fixed**: `snapshotAll` (src/library.cpp:224-245) the anchor is now the newest revision whose content differs from the current working file — an auto-recorded infected revision (hash equals the current working bytes) is skipped, so the anchor stays on the pre-infection clean revision; if every revision equals the current content (unchanged asset / false positive), it conservatively keeps the newest revision and preserves the current content as restorable history. Regression test `snapshotAnchorSkipsInfectedAutoRecord` (tests/security_test.cpp); ctest `security_sentinel` passed (1/1 green); test functions 9/9 green; commits 687bc87 + 9278b43
- [x] Audit finding: `Library::hardenObjects` is public API documented as "hardening existing objects on open" (src/library.h:50; 85-antiransom.md:12), but this diff has no production call site (only tests/library_test.cpp:153 calls it), so opening an existing library never re-hardens old objects — inconsistent with the "idempotent re-hardening" doc promise (src/library.cpp:199,204; 85-antiransom.md:12). **Verified and fixed**: `Library` constructor now calls `hardenObjects()` (src/library.cpp:68-71), so opening an existing library re-applies read-only to writable objects (idempotent). Regression test `openingExistingLibraryHardensObjects` (tests/library_test.cpp, clears read-only then reopens and asserts the object is immutable again); ctest `library_history` passed (1/1 green); test functions 9/9 green; commits 687bc87 + 9278b43
- [x] Audit finding: `rollbackAll` used `anchorBytes.isEmpty()` as the "anchor revision vanished" guard, which is unreliable — if the anchor revision's content is itself empty bytes (a legal object), `readObject` returns an empty `QByteArray`, misread as "anchor vanished", so `continue` skips that asset and silently fails to roll back (src/library.cpp:277-280). **Verified and fixed**: `rollbackAll` (src/library.cpp:289-297) now uses revision-id existence (`anchorFound`) rather than content emptiness to detect a vanished anchor, so an empty-content anchor rolls back normally. Regression test `rollbackHandlesEmptyAnchorObject` (tests/security_test.cpp, import empty file → snapshot → overwrite → rollback → assert empty content restored); ctest `security_sentinel` passed (1/1 green); test functions 9/9 green; commits 687bc87 + 9278b43
- [x] Audit finding: `MainWindow::rollbackToSnapshot` label construction `QStringLiteral("#%1 %2 · %3 个素材").arg(snapshot.id).arg(snapshot.created, snapshot.assets)` — the two-arg `QString::arg(const QString&, int)` overload treats `snapshot.created` as the string and `snapshot.assets` as `fieldWidth` rather than substituting `%3`, so `%3` remains a literal; confirmed (output `#5 2026-10-31T00:00:00 · %3 个素材`), snapshot list labels miss the asset count (src/mainwindow.cpp:286). **Verified and fixed**: `src/mainwindow.cpp:286-289` changed to three chained `.arg()` calls (`.arg(snapshot.id).arg(snapshot.created).arg(snapshot.assets)`), so `%3` correctly substitutes the asset count; build passes, ctest green (library_history + security_sentinel 2/2); commits 687bc87 + 9278b43
- [x] Audit finding: when a `snapshotAll` anchor is an empty-content object, the `append` branch `readObject(hash) != bytes` returns an empty `QByteArray` equal to `bytes` (empty), so no failure is raised, but `hardenObjects`/`makeImmutable` still run on the empty object; this path is itself fine, yet combined with the `rollbackAll` `anchorBytes.isEmpty()` misjudgment it forms the "empty object cannot roll back" composite defect (see above) — the recommendation is an explicit existence/revision-id check instead of content-nonempty (src/library.cpp:280). **Verified and fixed**: `rollbackAll` (src/library.cpp:289-297) uses revision-id existence instead of content emptiness, so empty-content anchors roll back normally; the composite defect is eliminated — both `snapshotAll` empty-anchor and `rollbackAll` revision-id check work.
