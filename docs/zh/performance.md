> 状态：**草案，未拍板**。本文为 todo P-004 起草，目标是形成可验证阈值。2026-11-27 已在本机完成一轮实测（见下方「实测记录」），实测结果只是给 D-21/D-23 拍板的对照证据，本文阈值仍是草案；P-004 的验收仍需用户拍板后才可勾选。

## 实测记录（2026-11-27，Linux 开发机）

工具：`bench/bench_matrix.cpp`（`pentimento_bench_matrix`，不入 ctest）。用法：

```sh
cmake --build --preset dev --target pentimento_bench_matrix
./build/dev/pentimento_bench_matrix bench/run gen-only    # 生成样本矩阵（约 25 分钟）
./build/dev/pentimento_bench_matrix bench/run bench-only  # 实测七项阈值（约 25 分钟）
# 测完可删除：rm -rf bench/run（已 gitignore，不进仓库）
```

原始输出留档：`bench/results-2026-11-27.txt`（本表逐行来源，可直接复核）。同日另有一次近空闲条件复测（`bench/results-2026-11-27-idle.txt`）：导入 39.8 MiB/s、搜索 P95 414 ms、快照 125.4 s——三项未达未改善，说明瓶颈是结构性的，不是并行负载导致的假象。第三次按 D-23「每条件至少 100 次搜索」要求将搜索/筛选改为 120 次查询后复测（`bench/results-2026-11-27-d23.txt`）：导入 30.6 MiB/s、搜索 P95 425 ms、快照 116.9 s，三项仍未达。

环境：Intel i9-10880H（14 核），Qt 6.10.2，ext4/LVM，515 GiB 空闲。**注意：测量期间机器有并行编译负载（load avg 8–14），且进程有 ~9.5 GiB swap 在用，下列数字偏保守。** 样本矩阵按草案 8 类生成 2,590 个文件，实际 12,995 MiB（12.69 GiB，比草案名义 11,960 MiB 大 8.6%——噪声内容不可压缩，编码体积按像素数收敛到 ±30% 带内）。

| 指标 | 阈值（草案） | 实测 | 结论 |
|---|---|---|---|
| 首次导入吞吐 | ≥ 100 MiB/s | **31.5 MiB/s**（2,590 文件 / 12.69 GiB / 412 s） | 未达 |
| 缩略图生成 | ≥ 512 张/分钟 | **1,661 张/分钟**（1,000 张 / 36.1 s，PNG/JPEG ≤1 MiB） | 达标 |
| 名称搜索 P95 | < 200 ms | **377 ms**（2,590 资产） | 未达 |
| 组合筛选 P95 | < 500 ms | **403 ms** | 达标 |
| 时间轴打开（100 版本） | < 500 ms | **1.0 ms** | 达标 |
| 整库快照（内容未变） | < 10 s | **126.4 s**（2,590 资产） | 未达 |
| 恢复 64 MiB（含校验） | < 3 s | **2.5 s**（实际 55 MiB 样本） | 达标 |

分格式导入吞吐（MiB/s）：PSD 47.9、JPG 32.9、ZIP 33.0、PNG 27.6、BMP 25.6、TGA 29.7、WebP 18.1。

三条未达项的初步定位（供拍板，未改产品代码）：

- **导入 31.5 MiB/s**：小文件路径被每文件固定开销主导（哈希 + 对象落盘硬化 + SQLite 提交 + P-217 事实解码），2,540 个小文件摊薄了 6.4 GiB 大 ZIP 的顺序写带宽。是否逐项优化（fsync/chattr 批量化等）属产品决策，不是本轮范围。
- **名称搜索 377 ms**：当前实现即 UI 真实路径（`assets()` + 逐资产 4 次目录查询构造事实 + 纯内存 `filterMatches`），2,590 资产 × ~10k 次查询。若拍板维持 200 ms 阈值，需要事实缓存/单查询取数一类的优化。
- **整库快照 126 s**：`snapshotAll` 对每个工作副本无条件流式哈希（12.69 GiB ÷ 126 s ≈ 100 MiB/s 实测哈希带宽，本机 SHA-256 未走硬件加速）。草案 <10 s 隐含「内容未变可跳过」；跳过需 size/mtime 短路路径，属产品改动。

口径与草案一致：吞吐按对象写入字节/耗时；缩略图为完整生成、不含队列等待；搜索/筛选含目录查询、不含渲染；快照/恢复为核心库 API 返回时间。

## 建议阈值

| 指标 | 建议阈值 | 备注 |
|---|---|---|
| 首次导入吞吐 | ≥ 100 MiB/s | 本地 NVMe，排除源目录扫描以外的网络因素 |
| 缩略图生成 | 512 张/分钟 | 512 KiB PNG/JPEG/WebP |
| 名称搜索 | P95 < 200 ms | 2,000+ 资源 |
| 组合筛选 | P95 < 500 ms | 名称+标签+格式+尺寸 |
| 时间轴打开 | < 500 ms | 单素材 100 版本 |
| 整库快照 | < 10 s | 2,000 资源，内容未变化 |
| 恢复 64 MiB 文件 | < 3 s | 含哈希校验 |

## 可验证口径

- 吞吐以对象写入字节数/耗时计算，排除 UI 线程阻塞影响。
- 缩略图以完整生成完成为准，不含队列等待时间。
- 搜索/筛选以 SQLite 查询完成时间为准，不含界面渲染。
- 快照/恢复以核心库 API 返回时间为准，不包含对话框交互。

## 决策点

- D-20：样本总规模 30 GiB 是否可接受，是否需要降到 10 GiB/5 GiB 快速档。（草案总量已按 90-corrections C-01 修为约 11.68 GiB；2026-11-27 实测生成 12.69 GiB。）
- D-21：目标硬件是否仅按当前 Linux 开发机（NVMe/Qt 6.10）设定。（2026-11-27 已在本机实测一轮，七项四达三未达，见上方「实测记录」。）
- D-22：PSD 是否必须产出合成预览，还是仅原字节保留+降级状态。
- D-23：上述阈值是否需要按 Windows/macOS 分别放宽/收紧。（实测只覆盖 Linux；三未达项是否放宽阈值或投入优化，需拍板。）
