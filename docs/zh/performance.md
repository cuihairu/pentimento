## 实测记录（2026-11-27，Linux 开发机）

工具：`bench/bench_matrix.cpp`（`pentimento_bench_matrix`，不入 ctest）。用法：

```sh
cmake --build --preset dev --target pentimento_bench_matrix
./build/dev/pentimento_bench_matrix bench/run gen-only    # 生成样本矩阵（约 25 分钟）
./build/dev/pentimento_bench_matrix bench/run bench-only  # 实测七项阈值（约 25 分钟）
# 测完可删除：rm -rf bench/run（已 gitignore，不进仓库）
```

原始输出留档：`bench/results-2026-11-27.txt`（本表逐行来源，可直接复核）。同日另有一次近空闲条件复测（`bench/results-2026-11-27-idle.txt`）：导入 39.8 MiB/s、搜索 P95 414 ms、快照 125.4 s——三项未达未改善，说明瓶颈是结构性的，不是并行负载导致的假象。第三次按 D-23「每条件至少 100 次搜索」要求将搜索/筛选改为 120 次查询后复测（`bench/results-2026-11-27-d23.txt`）：导入 30.6 MiB/s、搜索 P95 425 ms、快照 116.9 s，三项仍未达。D-23 还要求「另测从操作到显示结果的用户等待时间与界面可响应性」——`bench/bench_ui.cpp` 驱动真实 MainWindow 搜索框（离线屏/120 次查询）。加了 10 次预热、完整应用先测、分离“过滤应用”与“界面稳定”的第三轮结果（`bench/results-2026-11-27-ui-warm.txt`）：完整应用 UI 稳定 P95 4,144 ms、仅搜索路径 1,452 ms，UI 定时器延迟 P95 4,113 ms。主要耗时是 `applyFilter` 对 2,590 个列表项同步 show/hide，而非数据库或重绘；完整应用还叠加 2 秒变更扫描定时器的停顿。是否保留 200 ms 预算、优化 `applyFilter` 或放宽预算需用户拍板。D-20「两档覆盖五种位图、PSD 降级和损坏样本」的损坏样本也已补齐：生成器新增 5 个位图截断样本 + 2 个 PSD 损伤样本，混合矩阵 2,597 文件/12.69 GiB 复测七项，三项结构性未达不变、恢复本轮 3,169 ms 刚越过 3 s（前几轮 2,484–2,718 ms，属运行间波动）；原始输出见 `bench/results-2026-11-27-bad-samples.txt`。D-20 同时要求样本清单写明数量、大小、图像尺寸、哈希与覆盖目的——清单见 `bench/samples-2026-11-27.csv`：2,597 个文件，按名称、格式、字节数、宽高、SHA-256 与用途（五类位图各 500、PNG 不透明/透明各 250、ZIP 50、大图 20、PSD 20、损坏样本 7）列出，合计约 12.69 GiB。D-20 的快速档（约 5 GiB，数量按比例缩减、覆盖面不变）也已生成并实测：`bench/bench_matrix.cpp` 新增 `gen-quick`/`bench-quick` 档位（每类位图 200、大图 8、PSD 8、ZIP 20 + 同一 7 个损坏样本，共 1,043 文件/5.08 GiB），清单见 `bench/samples-quick-2026-11-27.csv`。负载 5–11 条件下七项实测（`bench/results-2026-11-27-quick.txt`）：导入 30.5 MiB/s、搜索 P95 220 ms、快照 52.8 s 三项结构性未达按预期比例复现（快照 ≈ 5.08 GiB ÷ ~98 MiB/s 哈希带宽；搜索随资产数 2,590→1,043 从 377–501 ms 降到 220 ms），其余四项达标。同日一次负载 24–60 的污染轮次已弃用留档（`bench/results-2026-11-27-quick-loaded.txt`），不作为对照证据。

三条未达项的初步定位（供拍板，未改产品代码）：

- **导入 31.5 MiB/s**：小文件路径被每文件固定开销主导（哈希 + 对象落盘硬化 + SQLite 提交 + P-217 事实解码），2,540 个小文件摊薄了 6.4 GiB 大 ZIP 的顺序写带宽。是否逐项优化（fsync/chattr 批量化等）属产品决策，不是本轮范围。
- **名称搜索 377 ms**：当前实现即 UI 真实路径（`assets()` + 逐资产 4 次目录查询构造事实 + 纯内存 `filterMatches`），2,590 资产 × ~10k 次查询。若拍板维持 200 ms 阈值，需要事实缓存/单查询取数一类的优化。
- **整库快照 126 s**：`snapshotAll` 对每个工作副本无条件流式哈希（12.69 GiB ÷ 126 s ≈ 100 MiB/s 实测哈希带宽，本机 SHA-256 未走硬件加速）。草案 <10 s 隐含「内容未变可跳过」；跳过需 size/mtime 短路路径，属产品改动。

口径与草案一致：吞吐按对象写入字节/耗时；缩略图为完整生成、不含队列等待；搜索/筛选含目录查询、不含渲染；快照/恢复为核心库 API 返回时间。

### UI 等待预算（草案，供 D-23 拍板）

D-23「另测用户等待时间与界面可响应性，给出预算供批准」——实测（`bench/results-2026-11-27-ui-warm.txt`，2,590 资产、120 查询、含预热）与预算草案对照：

| 指标 | 实测 P95（完整应用） | 实测 P95（仅搜索路径） | 预算草案 | 达标前提 |
|---|---:|---:|---|---|
| 过滤应用（键入→过滤完成） | 2,975 ms | 1,452 ms | < 500 ms | `applyFilter` 异步化/虚拟化 2,590 项 show/hide |
| UI 稳定（键入→列表可见项就绪） | 4,144 ms | 1,452 ms | < 1 s | 同上 |
| UI 定时器延迟（可响应性） | 4,113 ms | 1,599 ms | < 250 ms | 2 s 变更扫描定时器让位或分片 |

**未拍板说明**：预算草案在现实现下全部不可达——主耗在 `applyFilter` 对 2,590 个列表项的同步 show/hide（纯搜索路径 1,452 ms 即全部来自它）与完整应用 2 秒变更扫描定时器的停顿；达标需产品改动（异步 show/hide、model/view 虚拟化、定时器分片），是否投入由 D-23 拍板。可选路径：(a) 采纳上表预算并投入优化；(b) 放宽预算接受现值；(c) 两者折中（如 UI 稳定 < 5 s 即现值达标）。以上均为草案，未拍板前不改产品代码。

## 可验证口径

- 吞吐以对象写入字节数/耗时计算，排除 UI 线程阻塞影响。
- 缩略图以完整生成完成为准，不含队列等待时间。
- 搜索/筛选以 SQLite 查询完成时间为准，不含界面渲染。
- 快照/恢复以核心库 API 返回时间为准，不包含对话框交互。

## 决策点

- D-20：样本总规模 30 GiB 是否可接受，是否需要降到 10 GiB/5 GiB 快速档。（草案总量已按 90-corrections C-01 修为约 11.68 GiB；2026-11-27 实测生成 12.69 GiB。两档均已生成并实测：完整档 2,597 文件/12.69 GiB、快速档 1,043 文件/5.08 GiB，见上方「实测记录」。）
- D-21：目标硬件是否仅按当前 Linux 开发机（NVMe/Qt 6.10）设定。（2026-11-27 已在本机实测一轮，七项四达三未达，见上方「实测记录」。）
- D-22：PSD 是否必须产出合成预览，还是仅原字节保留+降级状态。（支持结论证据已齐：同一份 PSD 样本记录见两档清单——完整档 20 个 psd-raw-preserved + 2 个 damaged-sample、快速档 8+2，尺寸/哈希/用途逐行列出；实现与测试见 `tests/library_media_test.cpp` `psdCompositePreviewDegradesAndPreservesFile`——Qt 6.10.2 无 PSD 编解码器，合成预览未产出，字节保留+降级显示为现状；有合成图/无合成图、损坏文件在清单中分开。是否放宽为必须合成预览由 D-22 拍板。）
- D-23：上述阈值是否需要按 Windows/macOS 分别放宽/收紧。（实测只覆盖 Linux；三未达项是否放宽阈值或投入优化，需拍板。）
