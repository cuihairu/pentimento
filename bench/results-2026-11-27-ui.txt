Interpretation:
- The user-visible wait is worse than the core measurement suggests: even with
  cached facts, keystroke-to-display P95 is 1.6–2.7 s on this machine. The
  dominant cost is the repaint of the 2,590-item list after every query, not
  the in-memory filterMatches (which the core run times at ~400 ms including a
  cold fact rebuild; cached facts make that part near-free).
- D-23's "另测从操作到显示结果的用户等待时间与界面可响应性" is now answered with
  measured numbers. The draft budget (<200 ms, search on 2,000+ assets) is
  missed by the real UI path; whether to keep the budget, optimize the list
  repaint (e.g. only update affected rows / defer repaint), or accept a larger
  budget is a user decision — this file is evidence, not an approval.
- Run-to-run variance is large (startup 88.8 s this run vs 171.1 s previously,
  P95 varies ~1.6–2.7 s); the load profile on this machine is not clean, so
  treat these as order-of-magnitude UI numbers, not exact budgets.
